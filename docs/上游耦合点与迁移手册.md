# 上游耦合点与迁移手册

> 触发来源：2026-09-22 维护者问「DSH 之后更新了，我们不适配怎么办？是不是要花更多精力优化？」
>
> 这份文件的作用是把那个担心变成**清单 + 哨兵 + 流程**：上游动了哪一处、我们怎么降级、
> 改哪一行、怎么复跑验证。**目的不是预言上游会不会改，而是让"改了"这件事可观测、可定位、可估量。**

## 0. 一句话结论

本插件对宿主的耦合只有 **7 个接口**，且每个都有降级路径；**第三方运行时依赖 0 个**
（全库只 import 自己的 `core/` 与 `node:fs`/`path`/`os`/`crypto`）。
所以上游更新最坏的结果是"某段不注入 / 某个功能静默缺席"，**不是 DSH 起不来**，
要改的行数在**几十行以内**，且全部集中在 `adapters/`。

真正的风险不是"上游会改"，而是**我们自己跑的组合落后于发布组合**，导致风险不可观测。
对策是第 3 节的版本哨兵 + 第 4 节的升级自查。

## 1. 我们踩的 7 个宿主接口（含降级行为与改法）

| # | 接口 | 调用点 | 它干什么 | 断了的后果 | 上游改名时改哪 |
|---|---|---|---|---|---|
| 1 | `ctx.systemPrompt.section(spec)` | `adapters/dsh/sections.js:66` | 注册三个提示词段 | 段注册失败 → **吞掉并 `console.warn`**（0.14.0 起不再炸整棵树），最多少一段 | `sections.js` 里包 `section()` 与 `registerPersonaSections` 的注册循环 |
| 2 | 官方段名 + 顺序键 | `sections.js:173-174`（`deployment:persona-prefix` order 0 / `deployment:persona-suffix` order 10200） | 占官方具名槽位实现跨层遮蔽 | 段名失效 → 人设不再遮蔽部署级默认（可能两份并存） | `PRESET_SECTIONS` 常量一处；`resolveOrder(ctx.systemPrompt, orderKey, order)` 已做兜底 |
| 3 | `agent.options.model` | `sections.js:37`、`reflex/index.js:197` | 分档自称 / 按模型覆盖 / 规则档位 | 拿不到 = 空串 → 一律按 flash 档渲染 | 两处 `agent.options && agent.options.model` 取值表达式 |
| 4 | `agent.session.header.cwd`（回落 `agent.session.cwd`、`agent.options.cwd`） | `sections.js:38-40` | `{{cwd}}` 与记忆相关性选择 | 拿不到 = 空串 → 末尾段少一行、记忆按全局条目选 | `sections.js` 那三行 fallback 链 |
| 5 | `agent.session.id` | `reflex/index.js:199`、`271` | 会话级开关与命中台账 | 退化 `'unknown'` → 收口开关按"同一会话"处理会失真 | 两处 `(agent && agent.session && agent.session.id)` |
| 6 | `ctx.on('agent/pre-step')` / `ctx.on('agent/request')` | `reflex/index.js:185`、`271` | 条件反射层的两个挂载点 | 事件名变了 → 反射层整体不发（**可选层**，人设不受影响） | `reflex/index.js` 两个 `ctx.on(...)` |
| 7 | `agent.ctx.tools.restrict({allow})` | `reflex/toolnarrow.js`（引用 `dsh-tools/lib/index.js`） | 步级工具裁剪 | 拿不到 → 该步不裁工具（可选层），台账少 `savedChars` | `toolnarrow.js` 取 `tools.restrict` 的入口 |

**另有 3 个"软"依赖点**（拿不到就静默缺席，属设计内）：

| 接口 | 调用点 | 缺席后果 |
|---|---|---|
| `ctx.get('commands')` / `ctx.inject(['commands'])` | `sections.js:142-146` | `/memory` 命令不可用（注释原文：「拿不到 commands 服务时命令静默缺席」） |
| `ctx.webServer.register` + `ctx.effect` | `adapters/dsh-ui/index.js:215` | 设置面板不出现（引擎照常工作） |
| `ctx.slots.inject('settings.section')` / `ctx.slots.register` | `adapters/dsh-ui/client.js:1930-1950` | 面板不出现（同上） |

**UI 层的代价提醒**：`client.js` 是 1728 行、依赖宿主客户端运行时与 slot 契约，是**整个仓库对宿主最敏感的单文件**。上游改客户端插件 API 时，先看这里。

## 2. 上游**已经**发生过的改动（别人踩过，我们没踩）

证据来源：同类插件 `dsh-prompt-persona` 的 README「版本适配」表（2026-09 实际遇到的断裂点）。

| 上游改动 | 我们的暴露面 |
|---|---|
| `deployment:persona` **拆成** `-prefix` / `-suffix` | ⚠ **正面命中**（我们占的就是这两个）。我们已按拆分后的形态实现，且 `resolveOrder` 对顺序键有兜底 |
| `schemastery` → `@deepseek-ai/schemastery`（包改名） | ✅ 零暴露（我们不依赖任何 schema 包） |
| `dsh.client.inject` 里两个客户端包**已不存在** | ⚠ 部分暴露（UI 面板依赖客户端 slot API，但只在装 `dsh-ui` 时） |
| `settings.replace` 语义变（整段覆盖）→ 被迫改 `settings.update` | ✅ 零暴露（我们不通过 settings 服务读写，自己管 `config.json`） |
| profile 的 `node_modules/@deepseek-ai/` 一度是空的 | ✅ 零暴露（不自带 junction、不解析宿主依赖） |
| profile 层 `node_modules` 布局变化 | ✅ 零暴露（靠 `package.json` 的 `dsh.bundle.patch` 声明，不手搓路径） |

另一条同源证据：`dshworks/awesome-dsh-plugins` 的 registry schema 把 `verifiedAgainst`（"最后验证时的 dsh 版本"）
做成了**必填字段**，并在 schema 描述里写明 dsh 是 developer preview、**promised breaking changes**。
即：**上游一定会改是已知前提，不是意外**。

## 3. 版本哨兵：一条命令看清"上游变了吗"

```bash
node scripts/doctor.mjs          # 人读
node scripts/doctor.mjs --json   # 机器读（退出码非 0 = 有冲突级或不兼容级问题）
```

它除了原有的共存体检（段名/命令名撞车、重复 loader id、配置真源），还输出：

1. **宿主版本**（认包名 `@deepseek-ai/dsh` 找主包，不认硬编码路径；可用 `DSH_INSTALL` 指定）；
2. **本机各 profile 装的插件版本 + 挂载渠道**（npm / link-file / tarball）、以及"声明了但目录不存在"这种硬错；
3. **三段渲染实测**：拿**发布默认配置**跑 `core/edit.js` 的 `renderSections()`，
   断言三段长度为 `0/0/0` —— 把"装上零行为改变"从一句声明变成每次可复跑的检查；
4. **上游接口探测**：直接扫本机 DSH 的 `node_modules/@deepseek-ai/*`（本机实测 839 个文件 / 259 个子包，
   约 2–3 秒），逐个报第 1 节那些接口字符串还在不在，并给出命中位置。

**探测的性质要说清**：它是**文本包含**级证据，不是语义理解。命中 ≠ 接口语义没变；
**没命中一定值得看一眼**。它的价值在"上游一升级，十秒内知道哪一条先断"。

### 本机基线（2026-09-22 实测，DSH 0.1.6-alpha.2）

```text
· 宿主 DSH：0.1.6-alpha.2
· 上游接口探测：扫了 839 个文件 / 259 个子包 —— 7 个依赖点全部 ok
· 三段实测（发布默认）：0 / 0 / 0  ⇒ 零行为改变成立
· 退出码 0
```

顺带证实了一件事：`applyChildComposition` 在上游 `dsh-subagent/lib/index.js` 里命中 ——
**"人设能传给子代理"靠的是宿主自己的 preset 组合机制，不是我们的接口**（README 里那句
"本插件不调用任何 agent-team API"因此成立）。

### 同一台机器上可能有多套 DSH_HOME（2026-09-22 实测踩到）

本机就有两套，各自装了一套**不同版本**的本插件：

| DSH_HOME | profile 里声明的包名 | link 指向 | 实测版本 |
|---|---|---|---|
| 当前会话用的那份（`$DSH_HOME`） | `whale-persona` / `whale-persona-ui` | 该 home 下 `plugins/whale-persona` | 0.15.0 |
| 另一套（由启动脚本设定，端口不同） | `@shenA2024/whale-persona` | 该 home 下 `plugins/whale-persona` | 0.11.4 |

**为什么这是个坑**：两边都"装了"，看哪一边取决于会话进程的 `DSH_HOME`（由启动脚本设定，
有的启动脚本里写死）。只在其中一个 home 下验证，会得出"我这版没问题"的结论，
而实际跑的是另一个 home 下的旧版。

**哨兵已按此修正**：`installInfo()` 会扫**全部候选 home** —— `$DSH_HOME`、`~/.dsh`，
再按名字特征扫各盘根目录第一层（只认名字里带 `dsh` 的目录，**不写死任何具体路径**），
只保留其中有 `profiles/` 的；逐个列出包名、版本、link 指向的真实目录，
并标出哪一套是当前会话用的；有多套时给一行警告。

## 4. 升级后三分钟自查（照抄即可）

```bash
# ① 上游接口点还在不在（十秒）
node scripts/doctor.mjs

# ② 发布默认仍是零行为改变
node scripts/render-preview.mjs --config examples/empty-config.json

# ③ 全量测试与安全探针
npm test && npm run sec

# ④ 真机：新建一个会话，看人设段有没有进去（旧会话换不了 preset，必须新建）
```

**判读**：

| 症状 | 大概率原因 | 去哪儿看 |
|---|---|---|
| `doctor` 报某依赖点 `✗ 找不到` | 上游改了那个接口 | 第 1 节对应行的"改哪" + 该文件 |
| 三段实测不是 0/0/0 | 默认值被改坏了（**这是 bug，不是上游问题**） | `core/defaults.js` 的 `DEFAULTS` |
| 人设段全空、其它正常 | 段没注册上（接口 1/2） | `sections.js` 的注册循环 + 宿主日志里的 `console.warn` |
| 人设进去了但自称不对 | 模型 id 读取变了（接口 3） | `sections.js:37`、`agent.options.model` |
| 反射规则不生效 | 事件名变了（接口 6） | `reflex/index.js` 两个 `ctx.on` |
| 面板不见了但引擎照跑 | 客户端 slot API 变了（软依赖） | `adapters/dsh-ui/client.js` |

## 5. 为什么代价可控（三条结构性原因）

1. **零运行时依赖**：上游任何包改名/重构都传不到我们身上 —— 我们压根不 import 宿主包。
2. **格式与实现分离**（见 [SPEC.md](../SPEC.md) §11）：`core/` 1750 行是宿主无关的渲染核心；
   上游怎么改，`core/` 都不动。要改的永远是 `adapters/`（DSH 侧 766 行 + UI 2056 行）。
3. **异常一律降级为空段**：所有段求值包在 try/catch，最坏是"没有人设"，不是"会话发不出消息"。
   这条有测试钉住（`tests/smoke.mjs` 等）。

**还有一条更根本的**：用户资产不在插件里。人设、契约、记忆都在 `config.json` / 预设卡 /
收件箱文件里，格式由 SPEC.md 定义。适配器全废了，重写一个适配器、或换一个宿主，
**资产零损失带得走**。内容与引擎分仓、格式与实现分离，价值就在这里落地。

## 6. 这份文件怎么维护

- 新增对宿主接口的依赖 → **必须**加进第 1 节的表，并同步 `scripts/doctor.mjs` 的 `UPSTREAM_DEPS`；
- 上游发生过一次断裂（从 issue / 别人的 README / 自己的实测得知）→ 记进第 2 节；
- 每次升级宿主后跑第 4 节，把结果更新到第 3 节的基线块，写明版本与日期。
